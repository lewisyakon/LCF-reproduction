## 2. 指标、单位与耗时口径

### 2.1 质量与通信量

- GSM8K 使用最终答案 Exact Match；HotpotQA 使用 Answer EM 与 token F1；HumanEval 使用 pass@1。
- 方括号为逐样本统计得到的 95% 置信区间。
- “平均通信量”采用 `logical_transmission_bytes`，即实际发送张量与线协议元数据之和，不含未传输的原始文本。
- 通信量使用十进制单位：`1 MB = 10^6 bytes`，`1 GB = 10^9 bytes`。本批结果的单样本均值均小于 1 GB，因此表中统一显示为 MB。
- 转换器参数量使用十进制量级：`1 M = 10^6` 个参数，`1 B = 10^9` 个参数；冻结的 Sender、Receiver 基座模型不计入转换器参数量。

### 2.2 分项耗时

表中耗时不是直接采用原始 E2E 字段，而是按各部分的均值重新相加：

1. **上游** = 提示组装与分词 + Sender prefill；
2. **转换** = 源侧池化（仅 LCF-X）+ Sender 打包 + Receiver 解包 + 源层映射 + 联合转换与 Cache 融合；
3. **下游** = Receiver 本地 prefill + Receiver 生成 wall time + 反分词；
4. **合计计算耗时** = 上游 + 转换 + 下游。

`joint_transform_and_fusion_cuda_ms` 已经包含降投影、非线性转换、升投影、head weighting、门控和 Cache 融合，因此不再重复叠加这些子字段。

这里的 Receiver 生成 **wall time** 是从生成开始到生成结束实际经过的钟表时间，中文可理解为“生成实耗时”。它不仅包含 GPU 上的 decode，还包含每步 token selection、CPU/GPU 同步、D2H 拷贝和生成循环调度。本文将 `receiver_generation_wall_ms` 作为下游生成阶段的整体耗时，因此不再另加被它覆盖的 `receiver_final_decode_cuda_ms` 或 token-selection 子计时，避免重复统计。

传输耗时在正式测试中没有记录，也无法在缺少带宽和网络时延参数时从字节数唯一确定。因此合计耗时不包含传输时间，平均通信量作为传输开销的代理指标单独报告。小于 1 秒的耗时用 ms，达到或超过 1 秒的耗时用 s。

### 2.3 测量环境

- Device 1：NVIDIA RTX PRO 6000 Blackwell；batch size 1；greedy decoding；thinking 关闭。
- HotpotQA Receiver 最大生成 64 tokens；GSM8K 与 HumanEval 最大生成 1,024 tokens。
- CUDA 操作用 `torch.cuda.Event` 计时，CPU 与 wall time 用 `time.perf_counter` 计时。
- Sender 与 Receiver 在同一张 GPU 上执行，报告的是计算耗时，不包含真实网络传输。

## 5. 主要观察

1. **LCF-X 显著降低通信量。** LCF 的平均通信量为 15.518–226.766 MB；LCF-X 的 M1/M2 固定约 0.230 MB，M3 固定约 0.295 MB。在相同模型组和数据集上，通信量约缩小 67.6–768.8 倍。
2. **LCF-X 存在明显的训练域偏向。** 它在 HotpotQA P1/P2 上表现较好，其中 P1 的三组 EM 均高于对应 LCF；但 GSM8K 与 HumanEval P1 通常低于 LCF。这与 LCF-X 只使用 HotpotQA bridge 互补证据训练一致。
3. **P3/P4 是当前 LCF-X 的明显失效区间。** 当 Receiver 缺少完整证据或完整任务时，HotpotQA P4 与 HumanEval P4 的质量几乎为零，说明固定全局摘要未能可靠恢复完整任务信息。
4. **模型方向影响明显。** M2 在多数 P1/P2 条件下质量最好；M3 在基础 LCF 的 HotpotQA、LCF-X 的 GSM8K 与 HumanEval 上明显较弱。
5. **耗时主要由下游生成决定。** 按包含 pooling 与封装/解封装的新口径，转换开销约为 18.51–73.12 ms；GSM8K 和 HumanEval 的总耗时变化主要来自 Receiver 生成长度。通信量虽然可作为传输成本代理，但在没有网络测量的情况下不能据此报告真实端到端传输时延。
